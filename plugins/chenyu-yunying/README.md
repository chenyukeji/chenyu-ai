# 晨玙 Amazon 运营插件

`chenyu-yunying` 是面向 Amazon 运营岗位的独立插件。它从产品开发文档、自有产品事实、产品素材和竞品链接出发，完成竞品研究、欧洲站 Listing 和逐图作图要求。当前版本为 `0.9.3`。

插件不登录或修改 Amazon 店铺，不自动发布 Listing，不执行广告投放，也不会把真实开发表、竞品快照、图片或任务输出写入插件源码和分发包。

## 当前包含什么

| Skill | 适合什么需求 | 主要输入 | 主要交付 | 不负责 |
| --- | --- | --- | --- | --- |
| `chenyu-yunying` | 不确定该用哪个能力，或同时需要 Listing 和作图要求 | 开发表、素材、目标站点、自然语言要求 | 统一产品事实并协调下面三个专业 Skill | 后台自动调度、广告投放、商品发布 |
| `chenyu-jingpin` | 抓取和整理竞品资料 | 开发表中的链接或单独提供的 Amazon 商品链接 | 标题、五点、普通/A+描述、主图/图册/A+图片及 `competitor-research.json` | 生成自有 Listing、复制竞品图片、抓品牌故事 |
| `chenyu-listing` | 生成欧洲站自有产品 Listing | 自有产品事实、目标站点、竞品研究包 | 默认 DE/FR/IT/ES 四站无品牌标题、五点、四段式详情、关键词和 Search Terms；UK 按需生成 | 抓取网页、发布商品 |
| `chenyu-zuotuyaoqiu` | 生成交接美工的逐图方案 | 自有事实、可选 Listing 与竞品视觉证据 | “产品内容＋作图要求”双表 Excel，每张图含目的、构图、文案、参考链接和验收条件 | 实际生成或精修图片 |

其中：

- Listing 标题统一为“3 个核心关键词＋主要场景”。三个词必须以原词或已确认的相似表达融入五点。
- 五点统一为“Emoji＋【本地语言小标题】＋2—3 句正文”。
- 详情统一为“产品概括、3—5 条特征、产品参数、包装内容”，默认纯文本。
- 同一任务中的竞品链接只抓取一次，Listing 和作图要求复用同一个研究包。
- 作图单默认采用两张轻量工作表：“产品内容”只保留变体事实，“作图要求”使用可点击参考链接与执行要求；不嵌入图片，不设“补充说明”或独立“自有产品素材”栏，默认规格为 1254×1254 px。
- 默认先确定七张图的任务顺序，再为每张图寻找匹配的竞品参考：主图、产品近照、尺寸图、使用流程或细节图、特点/优势或场景图、场景图、四宫格场景图。现有素材不能反向决定图序。
- 图片尽量无文字；必须写字时统一用精简英文。目标站点 Listing 仍使用对应站点语言。
- 用户提出综合 Listing 需求但未另行指定站点时，默认一次生成德国、法国、意大利、西班牙四站版本；各站独立本地化，不把德语稿机械逐句翻译。英国站仅在明确要求时加入。

```text

            ↓

       ┌────┴────┐

```

## 方法说明

### 1. 证据优先级

插件把“自己的产品事实”和“竞品提供的表达参考”严格分开。发生冲突时按以下优先级处理：

1. 用户在当前任务中的明确说明。
2. 开发文档中的自有产品文字、规格和变体记录。
3. 已确认归属于当前产品/变体的自有图片。
4. 已形成的自有产品事实记录及其来源位置。
5. 竞品 Listing、图片和 A+ 内容，仅用于关键词、表达和构图研究。
6. 通用语言与版式经验，只能帮助组织内容，不能创造产品事实。

竞品页面中的尺寸、材质、配件、功能、认证和品牌不会自动进入自有产品事实。无法追溯到自有证据的内容，要么省略，要么作为具体待确认项保留在受影响字段旁。

### 2. 产品事实如何形成

开发表先被解析为工作表、单元格、超链接、图片锚点和附件清单，再按变体建立事实记录。常用字段包括：

| 事实类别 | 示例字段 | 核对重点 |
| --- | --- | --- |
| 产品身份 | 产品名称、品类、用途 | 不能用竞品名称代替自有产品身份 |
| 规格 | 长、宽、高、直径、重量、容量 | 数值必须绑定真实测量部位和单位 |
| 材质 | 主体材质、表面材质、配件材质 | 材质不能推出未确认的性能 |
| 外观 | 颜色、图案、形状、结构 | 图片归属必须对应具体变体 |
| 包装 | 数量、主体、配件 | 场景道具不计入包装内容 |
| 结构 | 开口、接口、部件、固定方式 | 看不清或未说明的结构不能补画、补写 |
| 场景 | 使用位置、节日、环境 | 只采用产品事实能够支持的场景 |

每项事实保留 `confirmed`、`unconfirmed` 或 `conflict` 状态。只有 `confirmed` 内容才能进入买家可见 Listing 和正式图片卖点。

### 3. 竞品研究如何使用

`chenyu-jingpin` 按站点和 ASIN 去重，读取标题、五点、普通/A+描述、主图、图册和 A+ 图片，并形成统一研究包。下游只读取这一个研究包，避免 Listing 和作图要求分别抓取后出现证据不一致。

竞品证据分成两类：

| 证据类型 | 可以用于 | 不能用于 |
| --- | --- | --- |
| 文字证据 | 当地产品词、同义词、属性表达、字段分布、独立商品组频次 | 复制品牌、连续文案、竞品规格或功能声明 |
| 视觉证据 | 构图类型、信息层级、产品占比、场景关系、尺寸线表达 | 直接复制竞品图、商标、文案、错误外观或配件 |

抓取失败、字段缺失和访问受限都会保留状态。插件不会用搜索摘要补齐缺失页面，也不会把“抓到竞品”当成任务完成。

## Listing 生成方法

### 1. 从事实到 Listing 字段

每个站点和变体先建立以下映射：

```text
自有产品事实
      ↓
可验证的购买理由
      ↓
目标站点关键词与允许的同义表达
      ↓
标题、五点、详情描述、Search Terms
```

一个购买理由必须能回到具体产品事实。竞品高频但自有产品不具备的词不会被采用。一个事实可以支持多个字段，但不同字段承担不同任务，避免反复改写同一句话。

### 2. 标题依据

每个站点/变体选择 3 个不同的标题关键词和 1 个主要场景，按自然语言组织：

```text
核心产品词 + 重要属性/第二产品表达 + 第三关键词 + 主要场景 + 必要的变体标识
```

标题规则：

- 核心产品词优先使用目标站点最准确、最自然的品类表达。
- 尺寸、数量、材质和款式只在已确认且有助于识别产品时加入。
- 三个关键词不能只是同一个词的机械重复。
- 标题后半部分只保留一个主要场景，不堆叠无关节日、人群和用途。
- 子体标题写当前变体差异；父体标题只在父子体关系和变体主题已核实时提供。
- 默认不添加品牌、品牌占位符、竞品身份、促销承诺或主观“最佳”描述。
- 编辑长度只作为可读性目标；没有核实站点和类目规则时，不把固定字符数冒充平台硬限制。

标题中的三个关键词必须在五点整体中以原词或预先确认的相似表达得到自然支撑。插件会记录采用形式和所在条目，不能在写完后临时把不相关词认定为同义词。

### 3. 五点卖点依据

五点默认按照买家决策顺序分工：

1. 包装数量、尺寸、颜色和主要产品内容。
2. 材质、结构或已确认的产品特点。
3. 主要功能、使用方式或呈现效果。
4. 适用场景、人群或节日。
5. 使用步骤、保养、注意事项或另一个已确认的补充特点。

每条使用“Emoji＋【本地语言小标题】＋2—3 句正文”，并只突出一个主要购买理由。若第 3 或第 5 条没有可靠事实，改用其他已确认内容，不为凑齐模板编造性能、步骤或安全结论。

### 4. 详情描述依据

详情描述固定为四个信息块，便于跨站点检查：

1. 产品概括：产品是什么、主要特点和核心场景。
2. 3—5 条特征：展开外观、结构、用途或搭配信息。
3. 产品参数：只列已确认的材质、颜色、尺寸及测量部位等。
4. 包装内容：逐项列明实际数量和物品。

默认使用纯文本。场景中的人物、家具、礼物、植物和装饰品不会被写成包装配件。

### 5. 多站点本地化

综合 Listing 任务默认生成 DE、FR、IT、ES 四站，UK 按需加入。四站共用同一套产品事实，但不是把某一语言逐句翻译：

| 站点 | 核对重点 |
| --- | --- |
| DE | 名词大小写、复合词、语序 |
| FR | 性数、介词、冠词和重音 |
| IT | 冠词、性数和属性搭配 |
| ES | 西班牙当地用语、重音和自然搭配 |
| UK | 英式拼写和当地产品表达 |

各站分别处理产品词、属性词、标题语序、五点小标题、详情栏目名和 Search Terms。事实保持一致，但句式和卖点展开顺序可以不同。

## 关键词方法

### 1. 关键词从哪里来

关键词候选来自三部分：

- 竞品原词：目标站点竞品标题、五点和描述中实际出现的产品词、属性词和场景词。
- 自有事实词：尺寸、材质、颜色、图案、结构和包装等真实属性。
- 本地化语义词：与自有事实一致、符合目标语言习惯的同义表达和长尾组合。

只有已经抓取目标站点竞品并完成独立商品组统计时，才能声称某词在样本中出现了多少次。没有当地竞品样本时，只把词标为相关候选，不声称具有搜索量、排名、热度或转化验证。

### 2. 频次如何计算

竞品频次按“出现该词的独立商品组数量”计算：

- 同一商品标题、五点和描述重复出现多次，只计 1 个商品组。
- 同一父商品的不同抓取入口按研究包中的 `product_group` 去重。
- 同义词先保留原始证据，再在语义组层面汇总。
- 抓取失败或字段缺失不计为未出现，并保留样本分母。

频次帮助判断表达是否常见，但不等于搜索量、广告流量或转化率。

### 3. 关键词如何分配

| 字段 | 作用 | 选择原则 |
| --- | --- | --- |
| 标题关键词 | 建立品类识别和主要购买意图 | 每站 3 个不同主词，自然成句 |
| 核心关键词 | 适合前台自然覆盖的产品、属性和场景词 | 与事实直接相关，通常 10—20 个 |
| 长尾关键词 | 组合尺寸、属性、款式和场景 | 相关且具体，通常 10—15 个 |
| Search Terms | 补充标题未充分覆盖的同义词和意图 | 一行输出，排除无意义重复 |

所有关键词都要排除竞品品牌、ASIN、错误规格、无依据功能、主观宣传词和无关流量词。需要判断后台字段字节限制时，应以当前站点和类目的已核实规则为准。

## 作图要求方法

### 1. 先确定图片任务，再找参考图

作图要求采用“任务优先”逻辑：先确定每张图要解决的买家问题，再从竞品研究包和自有素材中寻找适合该任务的参考。现有素材只能确认产品身份、外观和可执行性，不能反向决定整套图应该做什么。

用户未另行指定时，默认七张图如下：

| 图序 | 默认任务 | 关键要求 |
| --- | --- | --- |
| 1 | 主图 | 纯白背景、完整售卖产品、无文字 |
| 2 | 产品近照图 | 产品清晰置于前景，叠加淡化的使用背景，默认无文字 |
| 3 | 尺寸图 | 绑定真实测量部位；除准确数值和单位外不加说明文字 |
| 4 | 使用流程图或细节图 | 有可验证步骤时做流程；否则做结构/细节图 |
| 5 | 产品特点或优势图 | 只表现已确认且有区分度的特点；没有时改为场景图 |
| 6 | 场景图 | 一个清晰、自然、产品可见的典型场景 |
| 7 | 四宫格场景图 | 四个有区别的使用场景，产品身份保持一致 |

用户明确指定的数量、顺序和图型优先。某个品类不适用默认槽位时，应保留该槽位的销售目的，替换成最接近且可执行的图型。

### 2. 图片文字规则

- 能不使用文字就不使用文字。
- 必须使用文字时，默认统一采用精简英文，即使 Listing 使用德语、法语、意大利语或西班牙语。
- 单个标签或短语优先控制在 1—3 个词。
- 尺寸图只保留准确数值和单位。
- 流程图优先使用 01/02/03；确需动作词时使用极短英文。

### 3. 参考图如何选择

每张图先定义用途标签，再按用途筛选参考，例如：

- 主图：俯视或正视、完整轮廓、白底主体占比。
- 近照：产品前景与淡化使用背景的层次。
- 尺寸：测量箭头、数值层级、细节窗位置。
- 流程/细节：步骤关系或全貌加局部的结构。
- 特点：一个经过事实确认的差异化卖点。
- 场景：产品可见比例、环境透视和道具关系。
- 四宫格：多个场景之间的差异、统一性和阅读顺序。

竞品与当前变体在图案、颜色、结构和规格上逐项一致时，可以标为“同款产品参考”；否则只能标为“版式参考”。即使判定同款，也只能借鉴视觉外观，不能继承竞品品牌、尺寸、配件、文案或功能声明。

### 4. 缺少事实时如何降级

- 使用步骤不明确：从流程图改为结构或细节图。
- 没有可靠差异化优势：从特点图改为另一类场景图。
- 闭合方式不明确：不画绑带、魔术贴、纽扣等具体结构。
- 缺少会影响真实外观的证据：只在受影响任务内写明具体缺口，不建立通用“待补素材”区。
- 参考图不足：用文字明确构图目标，不编造不可访问的链接。

### 5. 多变体处理

多变体可以复用同一构图母版和参考链接，但图案、颜色或结构不同的变体必须分别生成成品。作图单会明确每个任务适用的变体、每款数量和不可改变项，避免把 A 款成品直接当成 B 款或 C 款。

### 6. Excel 交付结构

未指定模板时，作图交接采用两张轻量工作表：

- `产品内容`：每个变体一行，只保留确认事实和不可改变项。
- `作图要求`：图片顺序、参考例图 1、参考例图 2、完整执行要求。

工作簿不默认新增“审核说明”“补充说明”或素材图库页，不嵌入参考图或产品图，不设置独立“自有产品素材”栏。参考图使用可访问的商品链接或图片直链，并注明“同款产品”“版式参考”或“自有素材”。默认输出规格为 1:1、1254 × 1254 px。

## 一致性和质量检查

### Listing 检查

- 每个目标站点和在售变体都有完整 Listing。
- 标题含 3 个主关键词和 1 个主要场景，五点自然覆盖这 3 个词。
- 每套 Listing 恰好 5 条卖点，详情包含概括、特征、参数和包装。
- 数字、单位、材质、数量、颜色、图案和结构可追溯到自有事实。
- 各站语言自然，不混入其他站点语言或竞品身份。
- Search Terms 不含品牌、ASIN、错误规格和无依据功能。
- 连续长片段重复会提示复核，但未命中不等于证明原创。

### 作图要求检查

- 图序、图片数量、变体数量和最终成品数能够互相核对。
- 每张图都有明确目的、构图、文字、禁止项和验收条件。
- 参考链接与当前图型任务匹配，而不是因为素材存在就随意选用。
- 尺寸线绑定真实测量部位，单位换算一致。
- 场景道具不会被表现为包装内容。
- 图片文字遵守“尽量无文字、必要时精简英文”的规则。
- 不生成未经确认的结构、纹理、厚度、配件和性能。

## 方法边界

这套方法能提高事实一致性、本地化质量和美工交接效率，但不等于：

- 已验证目标站点的搜索量、广告流量或转化率。
- 已核实所有站点和类目的最新发布限制。
- 已取得竞品图片的复制或商用授权。
- 已确认未写入开发文档的材料性能、认证和使用方式。
- 已完成 Amazon 后台发布、广告投放或实际商品图制作。

需要发布级限制、当地词频或广告数据时，应在对应任务中接入最新官方规则或可靠数据源，再更新 Listing 和检查结果。

## 怎么使用

### 推荐：使用运营总入口

上传开发 Excel 和可用的自有产品素材，然后说明目标站点和需要的成果。例如：

```text
使用 chenyu-yunying，读取这份开发表里的产品信息和竞品链接，
为德国、法国站生成自有产品 Listing，并生成交给美工的逐图作图要求，不加品牌。
```

总入口会：

1. 只读解析开发文档，区分自有事实、变体、竞品链接和素材。
2. 有竞品链接时调用 `chenyu-jingpin`，只抓取一次。
3. 将同一个事实记录和研究包交给 Listing 与作图要求。
4. 核对名称、材质、尺寸、数量、变体和卖点的一致性。

### 直接使用专业 Skill

需求边界明确时可以直接指定：

```text
使用 chenyu-jingpin，抓取表格中的 Amazon 竞品 Listing、普通/A+描述和完整图片。
```

```text
使用 chenyu-listing，基于这份自有产品事实和竞品研究包生成德国站 Listing，不加品牌。
```

```text
使用 chenyu-zuotuyaoqiu，根据产品素材和已完成的 Listing 生成逐张作图要求。
```

### 建议提供的信息

- 产品开发 Excel 或已整理的自有产品事实。
- 明确的目标站点：DE、FR、IT、ES、UK 中的一个或多个。
- 产品名称、材质、尺寸及测量部位、颜色/图案、结构和包装内容。
- 每个变体是否在目标站点销售。
- 产品实拍、供应商图、版式参考及它们分别对应哪个产品或变体。
- 需要 Listing、作图要求、竞品研究，还是它们的组合。

必要事实缺失时，Skill 会列出具体待确认项；不会用竞品规格填补自有产品信息。

## 主要任务文件

任务文件应放在插件目录以外的独立输出目录，不进入 Git 或分发包。

| 文件/目录 | 作用 |
| --- | --- |
| `brief/manifest.json` | 开发表的工作表、单元格、链接、图片锚点、附件和警告 |
| `competitors/competitor-research.json` | 去重后的竞品 Listing、图片证据、抓取状态和来源 |
| `listing-package.json` | 自有事实、关键词映射、站点/变体 Listing 和引用关系 |
| `package-review.json` | Listing 完整性、格式、事实引用和站点/变体覆盖检查 |
| `content-review.json` | 关键词覆盖、长度、原词/别名位置和竞品长片段复核 |
| 作图要求文件 | 每张图的变体、目的、构图、文案、参考链接和验收条件 |

## 内置脚本

脚本使用 Python 3.10+ 标准库。以下路径均相对相应 Skill 目录，真实任务应使用插件外的输出目录。

```bash
# 解析开发 Excel
python skills/chenyu-yunying/scripts/extract_development_brief.py "input.xlsx" --out "task/brief"

# 抓取竞品 Listing 和图片
python skills/chenyu-jingpin/scripts/fetch_competitor_listings.py "task/brief/manifest.json" --out "task/competitors"

# 校验自有 Listing 包
python skills/chenyu-listing/scripts/validate_listing_package.py "task/listing-package.json" --out "task/package-review.json"

# 分析关键词覆盖、长度和重复片段
python skills/chenyu-listing/scripts/analyze_listing.py "task/listing-package.json" --out "task/content-review.json"
```

爬虫只访问任务提供的受支持 Amazon 商品页；遇到验证码、访问限制或字段缺失时记录 `partial/failed`，不会绕过限制或用搜索摘要补写内容。

## 目录结构

```text
chenyu-yunying/
├── plugin.json                       # 插件清单、版本和界面信息
├── README.md                         # 本说明
├── references/
│   └── kaifawendang.md               # 所有运营 Skill 共用的开发文档读取规范
└── skills/
    ├── chenyu-yunying/               # 运营总入口与 Excel 提取器
    ├── chenyu-jingpin/               # 竞品研究、爬虫和研究规范
    ├── chenyu-listing/               # Listing 写作、欧洲站本地化和校验脚本
    └── chenyu-zuotuyaoqiu/           # 逐图作图要求
```

每个 Skill 至少包含 `SKILL.md`。按实际需要增加：

- `agents/openai.yaml`：界面名称、简短说明、默认调用示例。
- `references/`：只在该 Skill 工作时需要读取的详细业务规范或数据契约。
- `scripts/`：需要重复、确定性执行的解析、抓取或校验程序。
- `assets/`：Skill 自带并会在输出中使用的模板、图标等静态资源。

不要建立空目录，也不要把真实业务样本放进 Skill。

## 如何新增一个 Skill

### 1. 先判断是否应该建 Skill

| 需求类型 | 应放在哪里 |
| --- | --- |
| 一个边界清楚、用户可单独请求、会产生独立成果的能力 | 新建 Skill |
| 只是某个 Skill 反复使用的确定性处理步骤 | 放进该 Skill 的 `scripts/` |
| 只是详细规则、字段说明或语言规范 | 放进该 Skill 的 `references/` |
| 需要读取 Amazon、ERP、素材库等外部实时系统 | 实现 MCP，并单独设计读取/写入权限 |
| 把多个 Skills 和人工确认点串成固定业务流程 | Workflow；实现前不要建空目录 |
| 代表一个岗位选择 Workflow、Skill 和工具 | Agent；等岗位流程与权限稳定后再实现 |

### 2. 创建目录和入口文件

在 `skills/` 下使用小写连字符名称，例如：

```text
skills/chenyu-guanggao/
├── SKILL.md
└── agents/openai.yaml
```

`SKILL.md` 最小结构：

```markdown
---
name: chenyu-guanggao
description: 清楚说明该能力处理什么请求、何时使用，以及不负责什么。
---

# Skill 名称

说明输入、处理规则、完成条件、交付格式和权限边界。
```

只有真正实现后才把新 Skill 加入插件；规划中的名称不能伪装成可用能力。

### 3. 接入运营总入口

新增专业 Skill 后同时更新：

1. `skills/chenyu-yunying/SKILL.md` 的任务分配表和共享工作流。
2. 本 README 的能力表、使用示例和目录结构。
3. `plugin.json` 的版本、说明和 `capabilities`（能力确实变化时）。
4. `AGENTS.md` 的仓库路由说明（如果仓库级路由发生变化）。

共享开发文档规则放在插件根目录 `references/`；仅属于新 Skill 的规则放在它自己的 `references/`，避免重复维护。

### 4. 验证

在仓库根目录运行：

```powershell
$env:PYTHONUTF8='1'
python "$env:USERPROFILE\.codex\skills\.system\skill-creator\scripts\quick_validate.py" "plugins\chenyu-yunying\skills\新-skill"
python -m unittest discover -s tests -v
```

至少检查：名称和目录一致、YAML frontmatter 有效、引用路径存在、脚本实际可运行、没有占位内容、没有真实产品数据、没有把尚未实现的 MCP/Agent/Workflow 写成可用能力。

## 更新现有 Skill

1. 先确认修改属于哪个专业 Skill，不把所有逻辑都堆进总入口。
2. 业务规则写入 `SKILL.md` 或对应 `references/`；可重复机械检查写入脚本。
3. 为新增的确定性行为补充测试。
4. 更新插件补丁或次版本号，并同步本 README。
5. 验证全部 Skills 和测试后再提交、推送、打包。

## 打包与安装

分发 ZIP 的根层必须直接包含：

```text
plugin.json
README.md
references/
skills/
```

不要在 ZIP 根层再套一层 `chenyu-yunying/`，也不要包含 `__pycache__`、`.pyc`、测试缓存、真实开发表、竞品图片或任务输出。

从仓库根目录用已提交版本打包：

```powershell
New-Item -ItemType Directory -Force outputs | Out-Null
git archive --format=zip --output="outputs/chenyu-yunying-0.9.3.zip" HEAD:plugins/chenyu-yunying
```

员工在支持插件上传的管理页面选择该 ZIP，安装或更新后新建对话使用。更新包时只需要重新分发 `chenyu-yunying`，不会影响美工、开发或采购插件。
